# Production Database Migration Policy

This project uses Payload CMS migrations as the canonical PostgreSQL schema history.

Baseline migration:

```text
20260727_101107_production_baseline
```

The baseline was generated by Payload `3.79.1` from the application config against an empty disposable PostgreSQL 17 database. The generated TypeScript migration, JSON snapshot and migration index are committed under `src/migrations`.

## Core Rules

1. Never run the baseline migration directly against the existing production database if its Payload tables already exist.
2. Take a verified database backup before adopting the baseline or applying a new production migration.
3. Never use `payload migrate:down`, `migrate:reset`, `migrate:refresh` or `migrate:fresh` against production without a separately reviewed recovery plan.
4. Treat local development databases as disposable sandboxes. Payload development push mode may keep them in sync automatically.
5. Every Payload schema change must include a committed migration before merge.
6. CI applies committed migrations to a blank PostgreSQL database and fails when the Payload config requires an uncommitted migration.

## Existing Production Database: One-Time Adoption

The current production database already contains Payload tables but may not have canonical migration history. The repository therefore includes a guarded adoption tool:

```bash
pnpm db:baseline:check
pnpm db:baseline:adopt
```

The tool does not run baseline DDL against existing content tables. It:

- obtains a PostgreSQL transaction-scoped advisory lock;
- verifies critical Payload tables and columns;
- verifies that `enum_users_role` contains `admin` and `editor`;
- checks existing migration history;
- refuses adoption when unexpected non-development migration records exist;
- removes Payload development markers with batch `-1` only during confirmed adoption;
- inserts the committed baseline into `payload_migrations` as batch `1`;
- creates only the `payload_migrations` history table and its indexes if that table alone is missing.

### Adoption Procedure

1. Create and verify a full PostgreSQL backup.
2. Deploy the code containing the adoption script without enabling automatic migration execution yet.
3. In the Coolify application terminal, run:

   ```bash
   pnpm db:baseline:check
   ```

4. Review the output. It must state that the production schema check passed and that the baseline is ready to adopt.
5. Run the confirmed one-time command:

   ```bash
   MIGRATION_BASELINE_ADOPT=20260727_101107_production_baseline pnpm db:baseline:adopt
   ```

6. Do not save `MIGRATION_BASELINE_ADOPT` as a persistent Coolify environment variable.
7. Verify migration status:

   ```bash
   pnpm db:migrate:status
   ```

8. Confirm that `20260727_101107_production_baseline` is reported as executed and no migration is pending.
9. Run the full non-public live smoke test before release.

If the check or adoption command reports an unexpected migration record or missing schema object, stop. Do not run `payload migrate` against that database until the mismatch is reviewed.

## Coolify Deployment Policy

After the one-time baseline adoption succeeds, set the Coolify production build command to:

```bash
pnpm build:deploy
```

`build:deploy` performs:

```bash
pnpm db:migrate && pnpm build
```

This ensures that:

- only committed, pending migrations are applied;
- a failed migration rejects the deployment;
- the application build does not continue against an outdated schema.

Keep the start command as the normal application start command:

```bash
pnpm start
```

Do not run migrations independently in multiple application replicas. Migrations should run once in the deployment build/pre-deploy phase.

## Fresh Database Procedure

For a new empty database:

```bash
pnpm db:migrate
pnpm build
pnpm start
```

The committed production baseline creates the complete schema. No adoption command is needed for an empty database.

## Future Schema Changes

When a collection, global, field, enum, index or relationship changes:

1. Complete and test the feature locally.
2. Generate a descriptive migration:

   ```bash
   pnpm db:migrate:create descriptive-change-name
   ```

3. Review the generated `up` and `down` functions.
4. Review the generated JSON snapshot.
5. Commit the new migration file, snapshot and updated `src/migrations/index.ts` with the feature.
6. Open a pull request.
7. CI must pass:
   - Payload type generation;
   - committed type check;
   - TypeScript and ESLint;
   - migration application on blank PostgreSQL 17;
   - migration status;
   - schema migration drift detection;
   - production build.
8. Back up production before deployment.
9. Deploy through `pnpm build:deploy`.

Do not manually edit an old migration after it has been applied to production. Add a new corrective migration instead.

## Rollback Policy

The initial baseline `down` function drops the complete Payload schema and is intentionally suitable only for disposable databases. It is not a production rollback mechanism.

For production incidents:

1. stop the deployment;
2. preserve logs and migration output;
3. restore the pre-deployment database backup when data or schema integrity is uncertain;
4. revert application code only when it remains compatible with the restored schema;
5. create a forward corrective migration for non-destructive fixes whenever possible.
