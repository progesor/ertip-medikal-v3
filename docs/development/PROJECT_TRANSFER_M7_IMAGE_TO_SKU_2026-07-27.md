## Next priority: configurable SKU rule engine

The next development priority is the SKU rule motor. Visual optimization is considered implemented, subject to production smoke verification.

### Existing SKU behavior

Current implementation is embedded directly inside `src/collections/Products.ts` in the product `beforeChange` hook.

Current behavior:

- product attributes are parsed from hyphen-separated text values;
- all values are combined with a Cartesian product;
- variants are generated only when `triggerVariantGeneration` is selected;
- variant title format is effectively `<value> mm <attribute>`;
- `Çap` and `Uzunluk` attributes receive a Punch-specific SKU transformation;
- other attributes fall back to concatenated values;
- `skuPrefix` and `skuSuffix` are appended;
- an existing variant is preserved only when its generated SKU matches;
- generated variants default to active;
- generation logic and Payload collection schema are tightly coupled.

### Current limitations

- Punch-specific logic is hardcoded as the default behavior.
- There is no selectable rule profile.
- There is no preview/dry-run before variants are replaced.
- There is no combination-count safety limit.
- There is no duplicate SKU or collision report.
- There is no explicit normalization policy per attribute.
- There is no configurable token/template language.
- Stable variant identity depends mainly on generated SKU.
- Manual fields may be difficult to preserve safely when a SKU rule changes.
- The pure generation logic is not isolated for focused unit testing.

## SKU engine compatibility requirements

The existing Ertip Punch behavior must remain available as a compatibility profile and must not silently change existing product SKUs.

Non-negotiable rules:

1. Saving an existing product must not regenerate variants unless the administrator explicitly requests it.
2. Existing Punch products must keep their current output under the legacy Punch profile.
3. Existing variant images, price, active state and other manual fields must be preserved whenever the same logical combination still exists.
4. The system must detect duplicate/colliding SKUs before applying changes.
5. A configurable maximum combination count must prevent accidental variant explosions.
6. Admin must see a preview before applying generated variants.
7. Invalid configuration must fail safely without replacing existing variants.
8. New schema changes require a committed Payload migration.
9. Generated Payload types and admin import map must remain committed and CI-verified.

## Proposed SKU engine shape

Suggested profiles:

- `legacy-punch`
  - reproduces current `Çap + Uzunluk` behavior exactly;
- `template`
  - generic token-based SKU construction;
- `manual`
  - disables automatic SKU/variant generation for the product.

Suggested configurable concepts:

- prefix and suffix;
- separators;
- attribute token order;
- decimal normalization;
- punctuation stripping;
- fixed text tokens;
- per-attribute aliases;
- uppercase/lowercase transforms;
- value mapping tables;
- title template;
- SKU template;
- maximum combination count;
- collision policy;
- preserve-existing-variant policy.

Suggested architecture:

```text
src/lib/sku-engine/
  types.ts
  combinations.ts
  normalize.ts
  profiles/legacyPunch.ts
  profiles/template.ts
  generate.ts
  reconcile.ts
  validation.ts
```

The collection hook should become a thin adapter around pure, testable functions.
